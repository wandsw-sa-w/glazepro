# Step AU — stormproof casements

Done 13 Oct 2026. Brief: `docs/step-au-stormproof-brief.md`.
Facts: `docs/integrate-L31115-stormproof.txt`.

**The headline finding holds.** Integrate has no stormproof pricing, labour,
production or allocator rule, and **no new formula was added**. Every figure on
SA, SC and SF comes out of GlazePro's existing casement formulas once the tree
carries the stormproof sections. I searched the snapshot's price, labour,
production, allocator **and** ironmongery rules for `is_storm_proof`,
`is_stormproof_casement` and `is_flush_casement`: **zero matches**. The only
readers are validation rules 42–46.

---

## 1. Data — `sql/step-au1-stormproof.sql`

The sash type (added only if absent), the twelve stormproof keys on the
casement profile, and the "Single Stormproof Casement" template (Integrate's
template 21: 499 × 999, one LH opener), its tree **generated by
`buildCasementFrame({ stormproof: true })`** so the template is exactly what
the board builds.

**The profile question, answered: the CASEMENT profile, not a separate
stormproof one.** A drawing loads exactly one profile (`default_profile_id`),
and converting a window to stormproof **and back** needs both sets of sections
available at once. Separate profiles would mean changing a drawing's profile
mid-edit and having nothing to restore the flush values from. Integrate does
the same — its casement profile carries both the flush and the stormproof
frame defaults — and GlazePro's casement profile already holds
`casementSashPart.stormProofOverlap` and `.stormProofLipThickness`, which
`sql/step-aq3` reclassified as profile settings. These keys join a set that is
already there.

**I could not read the live rows.** The brief says to check them with
`/dev/sql`, but `claude_readonly_query` admits only
`nathan.smith@wandsworthsashwindows.com` and my only credentials are the
smoke-test user; it answers `claude_readonly_query: not allowed for this user`
(I tried, to be sure). So every statement is written to be **safe whatever is
there**: `ON CONFLICT DO NOTHING` and `WHERE NOT EXISTS` throughout, nothing
overwritten, and section 0 prints what it found before anything changes.

**The key spellings are therefore NOT VERIFIED.** They follow the live
convention (`stormProof…` on the part, as `casementSashPart.stormProofOverlap`
already does). They resolve through a candidate list, so if Integrate's import
used other spellings, putting them at the front of `STORMPROOF_CANDIDATES` in
`src/drawingBoard/casementOpenings.js` is the whole change — check 4b in the
SQL prints what is there.

## 2. Board — converting

**Files:** `src/drawingBoard/stormproof.js` (new), `casementOpenings.js`,
`src/pages/DrawingBoard.jsx`, `renderElevation.jsx`

A **whole-window** Flush / Stormproof control, not a per-opening one, because a
stormproof window is stormproof throughout (Nathan, 13 Oct) — which is also
Integrate's "Set for all casement sashes". On: the frame and cill take the
stormproof sections and every casement sash becomes a stormproof sash. Off: the
flush values come back from the profile and the overlap is **removed, not
zeroed**, so nothing downstream can read a lap on a flush sash.

- **Transoms, mullions and direct glazed units are untouched** either way, as
  Integrate leaves them. A test freezes their stored values and checks they are
  byte-identical after a conversion.
- **A conversion the profile cannot supply changes nothing** and says what is
  missing, rather than converting the window to a frame of nulls. The
  resolution is all-or-nothing for the same reason: half a set would build a
  sash with a null bottom rail, which prices as zero timber.
- **A bottom rail the surveyor typed survives** both ways. Only a rail still
  sitting on one of the three profile values (flush 83, flush fanlight 62,
  stormproof 76) is moved.
- **Any opening added later is stormproof**: `changeOpening` builds one that
  way, and the picker already copies the opening it splits.
- **Resizing and the fanlight/column rules are exactly as flush** — a test
  widens a stormproof double and checks the mullion re-spaces to 545 as it does
  on a flush window.
- **The drawing** shows the sash lapped 7 mm over the frame on each side. That
  is all the overlap does.

## 3. Variables and validation

`is_storm_proof` now comes from the stored sash type, `casementTypeId`
'stormproof'. **Step AS read an `isStormProof` flag that nothing ever set**, so
rule 43 could never have fired; the flag is still honoured for any drawing that
carries it. `is_stormproof_casement` and `is_flush_casement` are computed from
the sashes instead of being hard `false`.

Rule 43 ("ADD QUOTE NOTE: Storm proof casement windows (not flush)") fires once
per stormproof sash on every window, as Integrate's does. Rules 42 and 44–46
evaluate and stay silent: 42 needs "not complete new", 44 a bottom-hung sash,
45 a tilt-and-turn operation and 46 a top-hung sash under 310 mm. **Nothing is
unevaluable.**

The fanlight bottom rail warning fires on SB's and SC's fanlights because they
keep the 76 mm rail, which is over 62. **That is correct** — the brief says so,
and Integrate shows it on its own stormproof fanlights.

### `is_replacement_sashes_range` — set FALSE, with the reason

Folded in from the Step AT report. GlazePro does not store Integrate's product
range at all (Step AG). The nearest thing is `typeOfWork = 'sash_replacement'`,
but that is a different field with a different meaning — what WORK is being
done, not which product range was sold — and **rule 12 is an ERROR**, so a
wrong inference would block a quote with a false error. False makes the rule
**evaluable and silent** instead of unevaluable, which is what the Step AT
finding asked for. A test proves it now evaluates on SA, Q and A.

To switch it on once the equivalence is confirmed, the comment gives the whole
change: `const is_replacement_sashes_range = is_sash_replacement`.

## A bug found and fixed on the way

`cloneWithNewKeys` spread a node **shallowly**, so a cloned opening shared its
`values` object with the original — editing A1's bottom rail in place silently
edited B1's as well. The board's own field handler replaces values immutably,
so the application never hit it, but a test did, and it was a trap for anything
that mutates. `values` is now copied.
