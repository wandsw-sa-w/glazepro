## 2. Engine

**Files:** `src/pricing/doorGeometry.js` (new), `src/pricing/computeVariables.js`,
`src/pricing/pricingEngine.js`, `src/pricing/partAllocator.js`,
`src/pricing/evaluator.js`, `src/pricing/casementGeometry.js`,
`src/pricing/defaultIronmongery.js`, `src/pricing/benchmarks/fixtureDoor.js` (new),
`src/pricing/benchmarks/index.js`, `src/pricing/benchmarks/benchmarks.test.js`.

Six things were wrong or missing, all of them silent:

1. **A leaf is not half the opening.** The two leaves **lap** at the meeting
   stile, so each is `(opening − clearances − gap + overlap) / 2` — FD1's 912.5.
   Clearances (3/3 top and bottom, 1/1 left and right), gap 5 and overlap 27 are
   **read from the profile**, not hard-coded; `doorProfileDefaults()` names every
   key it used and refuses to build when one is missing.
2. **`door_leaf_qty` and `new_door_leaf_qty` were hard 0**, and `is_door` looked
   only for `doorLeafPart`. A French door was not a door at all, so **every live
   door rule was silent**.
3. **`is_casement_window` now excludes a door.** FD3 has a fanlight in it;
   without this it was charged a casement frame and a cill it has not got.
4. **The `door_leaf` loop** (price *and* allocator) now sees the French leaf
   types. The allocator's door-leaf variables were placeholder keys no drawing
   has ever stored (`v.grossHeight`, `v.handedness`); they come from the part type
   and the geometry now, so the lock rules band on the leaf's real height.
5. **The allocated multipoint-lock parts price as IRONMONGERY, not components.**
   Integrate's lines are whole pounds × 1.05 — the Ironmongery Cost formula. A
   component line would have priced cost × length with no length: a silent zero.
6. **`contains()` did not exist in the price evaluator.** The live rule's
   condition is `contains(part_name, utile)`, so it could not evaluate at all and
   a door priced **no timber**. The function is Integrate's and the rule already
   called it. The validation engine has its own `contains()`, which asks a
   different question and is untouched.

**`is_front_door` is derived as false for this step** — it is `true` only for the
open-in door range (profile `open_in_doors`), which does not exist yet. A French
door is `is_single_and_french_doors_range` (profile `open_out_doors`) and
`is_french_door`. This matters because several live rules are gated on
`is_front_door` and would otherwise fire on the wrong range (see the rule table
below).

**Allocated sections.** New loop `allocated_section_part`, length in mm, priced at
`length / 1000` **unrounded** × cost, line to 2 dp:

| Section | Length |
|---|---|
| Utile67x96 | frame head + jambs: overall W + 2 × overall H |
| Utile63x200 | cill + door bottom rails: overall W + each leaf width |
| Utile63x120 | door stiles + top rail: per leaf 2 × leaf H + leaf W − 6 |
| Utile63x63 | fanlight (62 sections): sash W + 2 × sash H + 14 |
| Utile63x96 | fanlight bottom rail 86: sash W |

The `−6` and `+14` are **fixed offsets**, read once from the facts and commented
as such: across the size changes in the facts file every length moved exactly
with the sizes, so neither offset is a function of size.

The section table is **keyed by material** (`DOOR_MATERIALS`), so Accoya prices
can be added as data later without touching code.

**Doors get no timber volume lines at all** — tested explicitly, see below.

# Follow-up — 13 Oct 2026

## The SQL has been run, and two of the four files needed rewriting

**All four `step-az` files ran on the live database on 13 Oct 2026, by the
reviewer with Nathan's approval.** az2 and az3 ran as written. az1 and az4 are
the reviewer's rewrites, committed unchanged and attributed (`a6c5423`).

**az1 — the fourteen lock parts were missing from the live catalogue, and my
file did not add them.** Every part code an active `mpls_doors` allocator rule
names — RJZ2382, the RHZ16xx / RHZ22xx shootbolts and flushbolts, both
`WIN500xxxx` TruLocks and the RGE2105 threshold — was **absent from
`parts_catalogue`**. A French door priced on the live site would have lost its
**£190.05 of lock ironmongery**, and nothing offline would have shown it: the
fixture injects those costs through `partCostMap`, so the benchmarks passed. The
rewrite inserts all fourteen with Integrate's own names and costs, adds a check
query that returns no rows once every allocated part exists, and extends the
rollback.

This is the general lesson, and it is worth writing down: **a fixture that
supplies its own part costs cannot tell you whether the live catalogue has the
part.** The benchmark was green because the fixture was complete, not because
the database was.

**az4 — my panel SQL would have inserted definitions the panel could not use.**
Four faults, all mine:

- no `group_name` on the inserted fields, where every existing door and French
  casement definition has `group_name = part_type`;
- the two reference fields named **no option list**, so Door Type and Operation
  would have had nothing to pick from (`sash_type` / `sash_operation`, exactly as
  the reviewer's step-ay2 did for the French casement);
- `archHead`, `specialJoineryDetails` and `specialGlassDetails` were inserted for
  part types that **have no such properties** — nothing in GlazePro would have
  read them; they belong to a later, all-products step;
- the sort orders did not put the fields in Integrate's order, and the settings
  Integrate does not show (`typeId`, the gap, the overlap, the mullion settings,
  `defaultMuntinThickness`) were left visible rather than `role 'config'`.

The costs were **derived backwards** from Integrate's priced lines, because none
of the four codes was in `pf30-snapshot.json`, and then attached to codes by
reading the allocator rules' own labels. **The labels do not say what the part
is:** `RHZ1667` is labelled "Slave flush bolt" and is the **keep**; `RHZ1653` is
labelled "Slave hinge keep 1997–2139" and is a **shootbolt**. The fixture's
comment said in as many words that this was a reading and that two could be the
wrong way round — and three were.

**No total moved**, which is the point: 51 + 89 + 35 + 6 = 181 either way, so
FD1–FD3b were and are exact. What was wrong was **which part each line was for**,
and only Integrate's part list could settle it.

`"Ironmongery Cost"` is `round(cost × qty, 0.1) × 1.05`, and Integrate's
`round()` takes **decimal places, floored** — so `0.1` means whole pounds. The
real costs round to the same whole pounds as the guessed ones, which is why the
lines are unchanged to the penny.

**The pairing is now asserted, not commented.** `benchmarks.test.js` checks each
code against **its own** Integrate line, by name and to the penny, on all four
FD benchmarks. The group total alone could never have caught this.

## One thing the live tests do NOT prove, and should

`src/pages/dev/PricingBenchmark.jsx` builds its cost map as
`{ ...partCostMap, ...(benchmark.partCostMap ?? {}) }` — **the fixture's costs
override the live catalogue's.** So the four FD rows passing on the live
benchmark page does **not** show that `parts_catalogue` holds the Utile sections
or the fourteen lock parts: for those codes the page is reading the fixture, not
the database. It is the same blind spot that hid the missing lock parts in the
first place, one layer further out.

What does prove it is **az1's own check queries**, which the reviewer ran: the
`mpls_doors` query returns no rows when every allocated part exists, and the
section query lists the five Utile costs.

**For the reviewer to decide:** now that both sets of parts are live, that
override could be dropped (or inverted, so live data wins and the fixture map is
only a fallback) — at which point the benchmark page would fail loudly if a part
went missing from the catalogue. It is a one-line change but it changes what
every benchmark on that page means, so it is not mine to make here.
